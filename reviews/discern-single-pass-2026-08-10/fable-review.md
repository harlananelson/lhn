**Verdict:** APPROVE with changes — the diagnosis is sound and tag+explode is the right fix, but the push-subsetting companion carries an unverified broadcast-semantics risk and should be decoupled from the critical path, and the runtime estimates don't guarantee the acceptance criterion.

## Must-fix before implement

1. **Decouple §4.3 (push_discern subsetting) from the scan fix.** The plan calls it a "required companion," but it is an optimization with its own unverified failure modes, and the scan fix alone is what unblocks #47. Land single-pass `extract_concept_events` as PR 1; land subsetting as PR 2 gated on the smoke checks in item 2. Coupling them puts an optimization's risk on the critical path.
2. **Verify subsetted-push semantics on HDL before relying on §4.3.** Two specific unknowns the plan asserts rather than verifies:
   - Foresight's docstring says push "broadcasts the given Discern context … **if it has not already been broadcast**." If the same context GUID is pushed twice in one Spark session with *different* concept subsets (two ExtractItems in one notebook, e.g. 035's labEvents then another item), the second broadcast may no-op and the second caller's concepts are simply absent. Full-context pushes are immune to this by construction; subsetting introduces it. The plan's per-call union of concepts per context handles within-call, not across-call.
   - The plan claims "if a concept name is wrong, crash still happens (same as today)" (§4.3 Risk). With a subset load, an unknown name may instead be silently ignored at load, converting today's loud `Py4JJavaError` into a **silent zero-row extraction** — the worst failure mode for this pipeline. Add a deliberate negative test (bogus concept, subsetted push) to the HDL smoke.
3. **Lock the default variant to explode-then-`isNotNull`, not higher-order `filter`.** Both are one scan; the perf difference (emitting then filtering N−1 null rows per non-matching row) is pure pipelined CPU, negligible next to the scan and UDF cost. The fallback uses only primitives already proven in this codebase on 2.4.4; the HOF variant adds a "confirm on HDL" step to the critical path where a failed run costs a platform day. Keep the HOF variant out of v1 entirely rather than as dead-code preference.
4. **Add a real behavioral offline test via a stub UDF.** §6.1 says end-to-end testing is "hard without UDF" — it isn't: `spark.udf.register('has_concept_in_context', stub)` with a dict-backed Python stub and a plain-string code column makes `F.expr` resolve exactly as on HDL. That enables offline verification of the actual contract: multi-match row multiplication, same-flag duplicates (the 066 `echo` case), no-match drop, null-code behavior, nested `retained_fields` aliasing. Structural expression-count tests alone don't test semantics.
5. **Reconcile the runtime math and the exec-timeout before declaring acceptance criterion 6.** The regression note is internally inconsistent: "one pass ≈ 8h at that rate" vs "four passes is ~12h" vs "~12h to ~3h." If one pass is really ~8h, even the fixed notebook busts a 21600s (6h) `--exec-timeout` and fails the platform day. The re-queue step (§6.3) must set an explicit `--exec-timeout` based on a measured smoke rate, dispatch early in the day, and pre-stage the phase-2 any-gate as the contingency rather than a someday option.
6. **Add `flag`/`_flags` collision validation.** `extract_concept_flags` validates flag names against `index_fields`; the events path validates nothing analogous. A retained/index field literally named `flag` (or `_flags` in the intermediate) produces a duplicate-column `AnalysisException` at write time today and would under the new plan too. Cheap guard, mirrors the sibling method.

## Should-fix / nits

- **Explain-plan structural assertion** in tests: assert the physical plan for the result contains no `Union` node (parseable from `result._jdf.queryExecution().simpleString()`). Directly tests the regression, cheap, works offline with the stub UDF.
- The diagnosis actually **understates** the cost: each union branch repeats the cohort join too, so it's N scans *and* N shuffles/joins. Worth stating in the PR description — it strengthens the case.
- Note in the docstring/changelog that dropped-field warnings now fire once (resolved against `source_df.columns`) instead of once per branch, and that output row order / output file counts will differ (interleaved source order vs branch-concatenated). No caller should care; say so explicitly.
- For very wide `concept_flags` (dozens of rows), the single when-array expression could hit whole-stage-codegen method-size limits and fall back to interpreted evaluation — correct but slower. One-line note; 4 concepts is nowhere near it.
- Phase-2 any-gate: the gate arrays and the tag exprs must be generated from the **same** resolved `concept_flags` structure, in one place — a hand-maintained gate list that drifts from the tags silently drops rows. Note also that matching rows pay each UDF twice (gate + tag).
- Open decision 1: agree with the default — keep union semantics (duplicate same-flag rows) in v1. `array_distinct` is a behavior change and downstream distills anyway.

## Answers to the 10 questions

1. **Diagnosis** — Real and correctly attributed. Spark 2.4.4 (and Spark generally) does not share a file scan across union children carrying different filter predicates; exchange/scan reuse only applies to identical subplans. Caveats: (a) caching the windowed+joined source could theoretically share the scan, but the plan rightly rejects it — the shared-shell memory rule makes caching an 88k-task table hostile, and 2.4 re-scan behavior under memory pressure is unreliable; (b) the diagnosis understates: the cohort join is also repeated per branch. The 88k-task stage evidence is consistent. Total UDF work is unchanged by the fix (N predicates per row either way); the win is I/O and shuffle, which is the dominant cost — the diagnosis gets this right implicitly.
2. **Algorithm** — Tag+explode is correct and is the same shape as `_flags` and the old `add_concept_indicators`+stack path. Edge cases handled: same flag twice (preserved as duplicates, correctly documented), multi-match (row per matching flag), empty flags (validated upstream), null code structs (a null UDF result yields a null tag → filtered, matching the union path's null-filter semantics). Missing: `flag`/`_flags` name-collision guard (must-fix 6). The single resolution of keep-exprs against `source_df.columns` is equivalent to today's per-branch resolution since all branches share the source.
3. **push_discern subsetting** — Directionally right (matches old production and Foresight's stated memory rationale) but not yet safe to require: re-push-same-context-different-subset semantics and unknown-concept-under-subset behavior are both unverified, and the second could turn a loud crash into a silent empty table (must-fixes 1–2). Land it separately, after smoke verification, with the cross-call hazard documented.
4. **has_any prefilter** — Worth it only when match rate is low and per-row UDF cost dominates after the scan fix — i.e., measure 066 first, exactly as the plan says. No bad interaction with tags *provided* the gate arrays derive from the same resolved `concept_flags` in one code path; drift between gate and tags silently drops rows. Matching rows pay double UDF evaluation.
5. **API/contract** — No breakage for 066/035/055: signatures unchanged, output columns and grain identical, config shape unchanged, raw-struct requirement unchanged, `_flags` path untouched. Must stay identical: column set and order (`keep…, flag`), multi-match multiplication, nested-field aliasing convention, validation errors, auto-write behavior. Acceptable visible differences: row order, output file counts, warning multiplicity — state them in the changelog.
6. **Spark 2.4.4** — Recommend **explode-then-null-filter as the default** (must-fix 3). HOF `filter` does exist in 2.4 SQL via `F.expr`, but it buys almost nothing here and adds a verification step to a critical path where verification costs platform days.
7. **Testing** — Offline plan is under-powered as written; the stub-UDF registration trick (must-fix 4) upgrades it from structural to behavioral, and an explain-plan no-Union assertion pins the regression itself. HDL smoke is right-shaped; add the negative subsetting test and capture a measured rows/sec to set 066's exec-timeout. The optional `_legacy_union` A/B flag is correctly rejected — a smoke cell can inline the old loop for a bounded count-compare without shipping dead code.
8. **Underweighted risks** — (HIGH) subset re-broadcast no-op across calls in one session; (MED) silent-empty on typo'd concept under subsetting; (MED) single pass may still exceed the 21600s exec-timeout given the operator's own ~8h/pass figure; (LOW) `flag`/`_flags` collisions; (LOW) codegen width for large flag lists.
9. **Agent** — Grounded Claude-tier implementer in the lhn repo (worktree branch → PR through lhn's review gate); Grok/AskSage as independent reviewers only; no small-tier or ungrounded implementer. See Agent recommendation above.
10. **Verdict** — APPROVE with changes. Required checklist: (1) split §4.3 into its own PR off the critical path; (2) HDL verification of subset-push semantics incl. negative test before PR 2 merges; (3) explode+`isNotNull` as the sole v1 variant; (4) stub-UDF behavioral tests + no-Union plan assertion; (5) measured exec-timeout and early dispatch for the 066 re-queue, phase-2 gate pre-staged as contingency; (6) flag-name collision validation.
